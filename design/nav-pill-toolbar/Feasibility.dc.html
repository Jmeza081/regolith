Can the pill be the toolbar?
Yes — and three of the four things it needs are already in the codebase. What it costs is not engineering, it is a behaviour you already designed on purpose.
Already true today
SelectionStore is @Singleton
The selection is app-scoped, not screen-scoped, so the nav graph can observe it directly. No new plumbing.
canSelectHere in NavGraph
The graph ALREADY computes whether this destination can act on a selection. That is exactly the gate a nav-level toolbar needs.
LocalNavChromeHold
Built this session so a message can keep the chrome on screen. A toolbar needs the same thing, permanently.
Four SelectionBar call sites
Library twice, Search, Browse. Moving it into the chrome makes that ONE. This is the real prize, not the animation.
Three shapes
1 · Morph
Tabs become verbs in the same 62dp pill.
Boldest, and the cheapest to draw. But 375×62dp cannot hold a count AND four verbs AND a way out — something has to be an icon with no label.
Breaks picking across tabs: you cannot reach Library while the tabs are gone.
2 · Stack  ●
A contextual tier docks above the pill, same blur, same family.
Tabs stay reachable, so a selection still spans Browse, Library and Search — the behaviour the shared store exists for.
Room for the count line AND four verbs. Closest to what is already shipping, re-homed.
3 · Expand
The pill's 50% radius animates into a 22dp card holding everything.
The most expressive, and the only one that feels like the pill BECAME something.
Tabs hidden while active, and the app's one blurred surface becomes a resizing one — the most expensive thing on screen, now animating.
What it would cost either way
• The pill auto-hides after three seconds; a toolbar must not. It would need a permanent hold, which is why NavChromeHold arriving this week matters.
• The pill is a navigation landmark to TalkBack. Swapping its contents mid-flight changes what that landmark means; a docked second tier does not.
• Scroll-to-hide has to stand down while selecting, or the toolbar vanishes under the thumb that is using it.
• Four screens stop owning their own bar. That is a refactor with real test surface, and worth doing once rather than per screen.
What I would do
Option 2. It buys the architectural win — one toolbar in the nav chrome instead of four bars in four screens — without spending the behaviour you deliberately built, which is that a pick survives walking between tabs. It is also the only one where the message tier and the verb tier are the same idea at two heights, so snackbars and selection stop being two systems. Keep Option 3 as the thing to try once the chrome owns the toolbar: by then the morph is an animation, not an architecture change.
